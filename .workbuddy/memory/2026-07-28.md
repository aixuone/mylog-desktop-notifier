## 主页面窗口（托盘点击弹网页）P1 四项 UX 需求实现

在 `main.js` 的 `openMainPage()` 落地以下四条（用户明确忽略：远程内容隔离/域名约束/配置放置/埋点）：

1. **关闭即隐藏，而非销毁**：`mainPageWindow.on('close')` 在 `!isQuitting` 时 `preventDefault()` + `hide()`；真正退出由全局 `isQuitting`（main.js ~45）控制。效果：× 或最小化后再次点托盘，仍是同一实例、继续原页面（满足"最小化再点开不重载"）。

## 故障诊断：客户反馈"消息通知只有铃声没有弹窗"

- 架构确认：弹窗是**自绘 BrowserWindow**（`lib/notificationCenter.js` 的 `preCreate()` 创建 `src/notification-center.html`），不是系统原生 toast。main.js 无 `setAppUserModelId`、无 `new Notification`，故 Windows「通知」「专注助手」设置与本 App 无关，别在那上面排查。
- 关键耦合：`pushMessage()` 第107-111行，`showWindow()` 与 `send('nc-play',{path})`(铃声) 在**同一个 `if(!blocked)` 块**内。有铃声 ⇒ 渲染进程已 `did-finish-load` ⇒ 窗口对象已创建且 `win.show()` 已执行。因此"有声无窗"几乎可断定是**窗口显示在了用户看不见的地方**，而非未创建。
- 头号嫌疑：`getNcRect()`(main.js ~409) 用 `screen.getPrimaryDisplay().workAreaSize`，弹窗永远贴在**主显示器**右下角。多屏时若主屏≠用户正在看的屏（如笔记本内置屏为主屏、外接大屏工作），窗口落在另一块屏；铃声走默认音频输出照样能听到 ⇒ 完美吻合"只有铃声没有弹窗"。窗口 `movable:false`，用户也无法拖回。
- 排除项：notifyMode 为 dnd/blockChat 时会同时禁声禁窗（第99行 `blocked`），既有声即非此模式；渲染进程已加载（否则无声），故排除 HTML 加载失败/空白窗。
- 定位步骤：①问客户单/多屏、主显示器是哪块、缩放%；②让客户看另一屏右下角有无白色小窗；③托盘右键→设置→通知模式须为"正常通知"；④确认铃声是 App 发还是网页自己发（若是网页自响+WS 弹窗失败则属另一路径）。
- **补充（单客户复现、Win10 关联排查）**：现象只在 1 台客户机出现，开发者本机+4~5 客户均正常 ⇒ 非代码普遍 bug，是环境差异触发。`notificationCenter.js:29` `alwaysOnTop:true` + `skipTaskbar:true` + `movable:false` ⇒ 窗口**必在最上层、不可能被遮挡**，故"有声无窗"只能是"弹在用户没在看的那块屏"。Win10 本身非根因但是催化剂：Win10 对接坞/拔屏后"幽灵显示器"残留、每屏不同 DPI 缩放处理比 Win11 糙；最典型场景=**笔记本合盖接扩展坞 + 主显示器仍设内置屏** ⇒ 白色小窗弹在合盖的内置屏右下角，看不见但铃声照响。确认话术：问客户"几块屏/主显示器是哪块/是否合盖用外接/主屏右下角有无小白窗"。

## 修复：视频会议屏幕共享不可用

- **根因**：`main.js` 从未注册 `session.setDisplayMediaRequestHandler`。Electron 中网页调用 `navigator.mediaDevices.getDisplayMedia()` 必须由主进程提供屏幕/窗口源，否则静默失败。视频会议 WebRTC 跑在主页面窗口（加载 `https://data.tygps.com/mylog-pc/`，用 `session.defaultSession`）。
- **改动**（仅 `main.js`）：
  1. 顶层 import 增加 `session, desktopCapturer`。
  2. 新增 `setupScreenShare()`：在 `session.defaultSession` 上注册 `setDisplayMediaRequestHandler`（调 `desktopCapturer.getSources({types:['screen','window']})` 后 `callback({video: sources, audio: 'loopback'})`）；并注册 `setPermissionRequestHandler` 仅对可信域名（tygps.com / localhost / 127.0.0.1）放行 `media` 与 `display-capture`，其余默认拒绝（最小权限）。
  3. `app.whenReady()` 中 `createTray()` 之后调用 `setupScreenShare()`。
- **注意**：`audio:'loopback'`（共享系统声音）官方注明当前仅 Windows 支持，本应用 win32 正合适；若会议同时用麦克风，留意回声（WebRTC 应用侧控制添加哪些轨道）。
- 验证：`node --check main.js` 通过；Electron 32.3.3 类型定义确认 `setDisplayMediaRequestHandler`/`setPermissionRequestHandler` 及 `Streams.audio: 'loopback'` 合法。未跑完整 GUI。

## 二次修复：屏幕共享「过程中发生未知错误」
- **现象**：点共享选源后网页端报"屏幕共享过程中发生未知错误，请重试"（即 `getDisplayMedia()` 的 Promise 被 reject 后 catch 兜的通用提示）。

- **修复**（`main.js` setupScreenShare）：`callback` 改为只返回 `{ video: sources }`，去掉 loopback；并加日志（请求来源 URL、sources 数量、getSources 失败原因），便于复现定位。

## 分析（不改代码）：托盘闪烁 + 消息弹窗不显示但能听到铃声
- **托盘闪烁根因**：`unreadCount>0` 驱动 `setTrayState('unread')` 闪烁。unreadCount 两路写入（main.js 1264 UPDATE_UNREAD_COUNT + notificationCenter pushMessage 经 onUnreadChange(=updateUnreadCount, main.js 989) 自增），终点都是 updateUnreadCount。「聊天框打开+对方发消息」时网页端因前台已读未必下发归零，但桌面端仍收 SHOW_MESSAGE_NOTIFICATION→pushMessage 自增(unreadCount+1)→闪烁卡住。桌面端以"收到通知事件"计未读、网页端以"会话已读"计未读，二者脱节。

## 修复问题1：托盘闪烁（已改代码）
- **改动文件**：`lib/notificationCenter.js` 的 `pushMessage()`。
- **做法**：移除 `pushMessage` 末尾的 `if (onUnreadChange) onUnreadChange(totalUnread())` 调用。`onUnreadChange`（=main.js `updateUnreadCount`）现仅由 `syncUnread`(SYNC_UNREAD 权威) 与 `markRead`(用户已读) 调用——即托盘未读只以网页端权威信号 + 用户已读为准，桌面端不再按"收到通知事件"自行累加。保留 `send('nc-unread', ...)` 故通知中心弹窗内列表仍正常显示。
- **原理**：桌面端是未读状态的消费方(sink)。开着聊天框时网页端已判读不再下发归零，但桌面收到 SHOW_MESSAGE_NOTIFICATION 仍自增→压过归零→常闪。去掉该自增即消除冲突。
- **验证**：`node --check lib/notificationCenter.js` 通过；grep 确认 onUnreadChange 仅剩 markRead/syncUnread 两处。未跑完整 GUI。
- **权衡**：若网页端对前台消息完全不下发 UPDATE_UNREAD_COUNT/SYNC_UNREAD，则真实未读经此路径的托盘即时性依赖网页侧信号；但现有 SYNC_UNREAD/UPDATE_UNREAD_COUNT handler 即为此设计，移除冗余自增符合架构意图。
