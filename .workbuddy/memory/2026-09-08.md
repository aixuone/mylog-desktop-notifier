# 2026-09-08

## macOS 关闭后再点托盘唤不起（续）—— 2026-09-07 的修复不够用
- 2026-09-07 修了 `app.dock.hide()` + 加 `app.focus({steal:true})`，但用户实测仍唤不起。
- 真正根因（macOS 上两个独立机制叠加）：
  1. **NSWindow 状态机卡在 "closing" 分支**：`close` 事件触发时 NSWindow 已被系统标记为 closing，紧接着 `hide()`（`orderOut:`）不会让状态机复位。后续 `show()`（`makeKeyAndOrderFront:`）因状态机仍卡在 closing 而被忽略。
  2. **`app.focus({steal:true})` 是异步激活 NSApp**：同步立即 `mainPageWindow.show()` 会被消息循环错过。
- main.js 修复（4 处）：
  1. `mainPageWindow.on('close')`：在 `hide()` 之后 `setImmediate` 调 `showInactive() + hide()` 一次，强制 NSWindow 状态机退出 closing。
  2. 托盘 click：macOS 上 `app.show() + app.focus({steal:true})` 后**延迟 50ms** 再调 `toggleMainPage()`，让 NSApp 激活生效。
  3. `toggleMainPage()` 与 `openMainPage()` 已存在窗口分支：macOS 上 `app.show() + app.focus({steal:true})` 后 50ms 延迟再 `show() + focus()`。
  4. 新增 `app.on('activate')` 监听 macOS Dock 图标点击（与钉钉/微信一致），同样 50ms 延迟调 `toggleMainPage`。
- Windows/Linux 不受影响：`process.platform === 'darwin'` 分支保护。
- 验证：`node --check main.js` 通过。
- 注意：close 拦截 + hide 保状态这条没动，HTML5 video / WebRTC / 表单状态仍保留。

## ⚠️ 上方理论被推翻 —— 真正根因是「macOS setContextMenu 劫持左键」
- 实测后仍唤不起，证明 NSWindow closing 状态机 / app.focus 异步都不是主因（那些 handler 压根没跑）。
- **真因**：`updateTrayMenu()` 里 `tray.setContextMenu(contextMenu)`。在 macOS 上，一旦设置了 contextMenu，**左键点击托盘会被系统解释为"弹出菜单"，`tray.on('click')` 不再触发**——所以"点托盘毫无反应、窗口唤不醒"。这是从最初（改 dock 之前）就存在的根因，之前多次修复都在治标。
- 2026-09-08 二次修复（6 处，已落 main.js）：
  1. `updateTrayMenu()`：macOS 不再 `setContextMenu`，改为 `tray.on('right-click', () => tray.popUpContextMenu(contextMenu))`；左键留给 `tray.on('click')`（toggle 窗口）。Windows/Linux 保持 `setContextMenu` 不变。
  2. `close` 事件：删掉之前加的 `setImmediate + showInactive + hide` hack，回归干净 `preventDefault + hide()`（那套复位反而添乱，且本就不需要）。
  3. `toggleMainPage()`：macOS 分支去掉 `app.focus({steal:true}) + setTimeout(50)`，改为 `app.show()`（NSApp.activate）+ 同步 `show()`/`focus()`。
  4. `openMainPage()` 已存在窗口分支：同样清理成 `app.show() + show/focus`，去掉延迟。
  5. 托盘 `tray.on('click')`：去掉 `setTimeout(50)` + `app.focus`，改为 `app.show()` 后同步 `toggleMainPage()`。
  6. `app.on('activate')`（Dock 点击）：去掉 `toggleMainPage` 的 toggle 语义，改为**只 show 不 toggle**（并保留 `app.show()`），避免"点 Dock 反而隐藏窗口"。
- 关键经验：**macOS 托盘想同时支持「左键唤醒 + 右键菜单」，绝不能 `setContextMenu`**，必须左键 `click` + 右键 `popUpContextMenu`。这是 Electron 在 macOS 上的已知行为。
- Windows/Linux 完全不受影响（`process.platform === 'darwin'` 分支保护 + 其它平台仍走 `setContextMenu`）。
- 验证：`node --check main.js` 通过。建议 macOS 实测：开窗→点×→点托盘=唤回；点 Dock=唤回；右键托盘=弹菜单。

## 核对：关闭窗口(hide)是否结束网页/视频会议
- 结论：**不会**。Electron `BrowserWindow.hide()` 只把原生窗口从屏幕藏起（`orderOut`/`ShowWindow(SW_HIDE)`），不卸载页面、不销毁渲染进程、不触发 reload。renderer 进程、WebRTC `RTCPeerConnection`、`<video>` 播放全部继续。
- desktop-notifier main.js 里**无任何** `on('hide')`/`on('blur')` 去 reload 或销毁主页面（唯一 reload 是顶部菜单「刷新」、唯一 navigate 是「关于」页手动「应用」）。`webPreferences.backgroundThrottling:false` 也开着。
- mylog-pc 前端 `visibilitychange` 核对（`web/src`）：仅 `AgentWorkspacePage.vue`（轮询启停）、`alertService.ts`（切回页面清标题闪烁）用到，**无任何"隐藏就暂停/挂断通话"逻辑**。故 hide 不结束会议/视频。
- 唯一风险只在远程网页自身的可见性业务代码，不在桌面端。

## 消息提示窗(通知中心)入场动效修复
- 现象：右下角通知窗"从上到下闪烁一下出现"，体验差。
- 真因：该弹窗是 `notificationCenter` 窗口（`src/notification-center.html`，非 legacy `toast-window.html`——后者 toastWindow 恒为 null 已废弃）。窗口先以 520 高度 `show()`，随后 `resizeWindow()` 经 IPC 把高度缩到内容高度 + 内容瞬间出现无入场动画，于是像"闪一下"。位置本身正确（构造时 x/y 即右下角，非跳位）。
- 修复（3 处）：
  1. `src/preload.js`：新增 `onNcShow` 通道（`ipcRenderer.on('nc-show')`）。
  2. `lib/notificationCenter.js` `showWindow()`：仅当 `!win.isVisible()`（隐藏→可见）时 `win.show()` 后 `webContents.send('nc-show')` 触发动画；已可见时收到新消息不重播，避免列表刷新反复闪。
  3. `src/notification-center.html`：加 `@keyframes ncSlideUp`（opacity 0→1 + translateY(28px)→0），`#app.nc-enter` 应用，`api.onNcShow(playEnter)` 强制重排重启动画，`animationend` 后移除 class 便于下次重播。效果=从下往上滑入+淡入。
- 验证：`node --check src/preload.js` 与 `lib/notificationCenter.js` 均通过。

## ⚠️ 通知窗闪烁 revisited —— CSS 滑入只治标，真因是原生窗口"先大后缩"的顶部下移
- 上一轮加的 `ncSlideUp`（28px 滑入）没解决问题：用户实测仍"整个窗口从上到下闪一下"。
- **真因**：`showWindow()` 先以满高 `H=520` `show()`（底对齐，顶边停在 `底部-520`），渲染层 `renderUnread` → `requestAnimationFrame(resizeWindow)` → `nc-resize` 把高度缩到内容高（如 360）。因 `getWindowRect` 底对齐固定，高度 520→360 时**顶边向下跳 160px**，表现为"窗口从上往下滑到右下角"。这是原生窗口跳跃，28px 的 CSS 动画根本盖不住。
- **修复（lib/notificationCenter.js，2 处 + 变量）**：引入 `pendingShow` / `showTimer`。`showWindow()` 在 `!win.isVisible()` 时**不再立即 show**，而是 `pendingShow=true` 并设 250ms 兜底；等渲染层回传 `nc-resize`（携带真实高度）后在 `nc-resize` handler 内 `setBounds` 到最终高度 + `show()` + `send('nc-show')`，使窗口**一次性以最终尺寸出现**，消除顶部下移。已可见时收到新消息仍不重播（不动 pendingShow）。
- 关键经验：bottom-right 通知窗要"先算高度再 show"，绝不能先 show 满高再 resize。preCreate 在启动时已渲染空态并静默 resize（隐藏态），不受影响。
- 验证：`node --check lib/notificationCenter.js` 通过。

## 麦克风没声音根因 + 权限修复（含手动授权兜底按钮）
- 现象：TRTC 通话 `startLocalAudio()` 报 `NotAllowedError: Permission denied`（code 5302），对方听不到；同份代码有的会话能开麦有的不能。
- 根因：Electron 媒体权限按 **origin** 隔离；主页面加载 `https://data.tygps.com` 跑 TRTC WASM 引擎，其内部以**程序化方式**查询/请求媒体权限，走的是 `setPermissionCheckHandler` 而非 `setPermissionRequestHandler`，而原代码**未注册 check handler** → 被静默拒绝（日志无任何 `[Permission]` 行，直接 `NotAllowedError`）。
- main.js 修复（1-4 全做）：
  1. 新增 `session.defaultSession.setPermissionCheckHandler`：对可信来源(tygps.com/localhost/file://)的 media/display-capture 直接放行（覆盖 WASM 内部路径）。
  2. `setPermissionRequestHandler` 放宽：主帧 URL 或 `details.requestingUrl` 任一受信即放行，避免子上下文/worker 非主页面 URL 被误杀。
  3. 启动预授权：主页面 `did-finish-load` 后 1.5s，在**主页面 origin 内** `executeJavaScript(getUserMedia({audio:true}))` 立即 stop，把权限置 granted（`micPreAuthed` 标志保证只跑一次）；失败仅记 warn。
  4. 手动授权兜底按钮：`activateMicrophoneInMainPage()` 复用同一引擎，`ipcMain.handle('microphone:activate')` 暴露，preload 加 `micActivate()`；诊断页 `src/diagnostics.html`「设备自检」卡片加「🔓 手动授予麦克风权限」按钮（id `btn-mic-activate` + `mic-activate-status`），在主页面域名下重新授权并回显结果。
- ⚠️ 关键坑：**手动授权必须在主页面 origin 内跑，不能在 file:// 设置/诊断窗口里直接 getUserMedia**——后者授权的是本窗口源，对主页面无效。所以一律走 `mainPageWindow.webContents.executeJavaScript`。
- 验证：`node --check main.js` + `src/preload.js` 均通过。

## macOS 摄像头/麦克风硬性前提补上（package.json）
- 发现：Electron 在 macOS 上访问摄像头/麦克风，应用 `Info.plist` 必须含 `NSCameraUsageDescription` / `NSMicrophoneUsageDescription`，否则 macOS TCC 直接拒绝（连系统弹窗都不弹），且 Electron 不自动补。原 `mac.extendInfo` 仅 `LSUIElement`/`NSHighResolutionCapable`，两个 usage 键均缺；entitlements 未开沙箱（无 app-sandbox）。
- 修复（package.json `build.mac.extendInfo`）：新增 `"NSCameraUsageDescription":"需要使用摄像头进行视频通话"` 与 `"NSMicrophoneUsageDescription":"需要使用麦克风进行语音与视频通话"`。
- 含义：此前 Mac 端摄像头/麦克风即便有 #1-#4 权限修复也会被系统层 TCC 拒绝；补齐后 + check handler 自动放行，Mac 摄像头/麦克风可用（首次访问走 macOS 标准一次性系统授权弹窗，批准后永久记住）。
- 验证：`node -e require('./package.json')` 解析 OK；`mac.extendInfo` 含 4 个键。`node --check main.js` 通过。
- 权限链路闭环确认：`setupScreenShare()`（main.js:591）内含 `setPermissionRequestHandler`(643)+`setPermissionCheckHandler`(658)，于 `app.whenReady`(1469) 调用；预授权(#3)在 `did-finish-load`+1.5s 跑 `activateMicrophoneInMainPage()`（1779-1789）；托盘「打开麦克风」(1108)→`microphone:activate` IPC(3059)→同函数。
- ⚠️ 已知非阻塞缺口：预授权与「打开麦克风」按钮仅 `{audio:true}`，摄像头靠权限闸门自动覆盖（无需手动按钮）；Mac 上若用户在 TCC 层曾拒绝摄像头，需到 系统设置→隐私→相机 手动重开（应用层无法绕过）。

## 媒体授权扩展为「麦克风+摄像头」独立双请求（用户批准）
- 用户批准把预授权与手动按钮从仅音频扩为同时覆盖摄像头。关键坑：**不能用单次 `getUserMedia({audio:true,video:true})`**——无摄像头机器会整体报错、连麦克风也授权不了（多数机器只有麦克风）。改为主页面内**音频、视频两次独立请求**。
