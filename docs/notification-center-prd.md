> 角色：产品经理（PM）
> 版本：v2.0（架构级重做）
> 状态：待验收
> 关联实现：`lib/notificationCenter.js`、`src/notification-center.html`

---

## 0. 为什么重做

前两版都在「修闪动」这个症状上打补丁：换成批次集合、换成时间过滤、键控复用 DOM……
补丁越打越多，但症状反复出现。复盘后确认**不是动画问题，是模型问题**：

- 旧模型里，"窗口里显示什么"由 **三个来源** 共同决定：`pushMessage`、`SYNC_UNREAD`、`markRead`，
  三者都能增删展示集合，也都能触发 `showWindow()` / `dismissWindow()`。
  谁先谁后都会得到不同结果 → 双通道推送时必然出现「刚弹出来又被清空再弹」的抖动。
- 旧模型里，"窗口该多高"由主进程**猜**（`lastHeight` 占位、250ms 兜底）。
  猜错就出现「先显示一条，下次刷新才显示两条」。

**本次重做的原则：每个状态只有一个写入者。**

| 状态 | 唯一写入者 | 其他人能做什么 |
| --- | --- | --- |
| 窗口可见性 | `pushMessage`（开启）+ 计时器/用户操作（关闭） | `SYNC_UNREAD` 仅在「未读增长且窗口未展示」时**兜底**开窗（见 §2.4），其余情况只校正内容 |
| 栈内展示项 | `pushMessage`（入栈）+ `SYNC_UNREAD`（仅校正/移除已读） | `MARK_READ` 只能移除 |
| 窗口高度 | 渲染进程实测 | 主进程只 `setBounds`，**不猜、不占位** |

## 1. 用户与目标

**用户**：Windows 上长时间挂着「我的日志」网页端 + 桌面端的人（值班、客服、项目经理）。
他们不在消息页，只靠右下角提醒判断"有没有人找我"。

**目标（按优先级）**

1. **不漏**：任何一条真实新消息都必须被看到一次。
2. **不闪**：提醒窗一旦出现，在本次提醒周期内**绝不会自己消失再出现**。
3. **能分辨**：多个会话同时来消息时，一眼看清是谁、几条。
4. **不打扰**：正在看的会话不提醒；免打扰会话不提醒；自己发的不提醒。

**非目标**

- 不做完整的消息列表 UI（只做"提醒"，不替代消息页）。
- 不做历史通知中心（收起即结束，不留档）。
- 不改动来电/会议窗口的交互。

## 2. 核心模型

### 2.1 一次提醒 = 一个「栈」

```
pushMessage(真实新消息) ──▶ 开栈 ──▶ 累积行（只增不减）──▶ 超时/用户操作 ──▶ 关栈（栈清空）
```

- **开栈**：只有 `SZEN_MESSAGE_NOTIFICATION`（网页端真实新消息）能开栈。
- **累积**：栈内条目只增不减（除"已读/归零"外）。同会话再来消息 → 更新该行，不新增行。
- **续期**：栈内任何新增或更新，都把关闭计时**重置为完整时长**（不是"剩余时长"）。
- **关栈**：超时自动关 / 用户 ✕ / 用户点最后一条 / 全部已读。关栈后 1.2s 冷却。

### 2.2 行位置规则（关键：稳定性优先）

- 新会话入栈 → **插到列表最上面**。
- 已有会话更新（新消息、计数变化、内容变化）→ **位置不动**，只改内容。

> 为什么不做"按时间重排"：重排会让整列跳动，肉眼即"闪"。用户关心的是"谁来了"，
> 而不是"严格按秒排序"。位置稳定 = 视觉稳定。

### 2.3 高度协议（消除"先一条后两条"）

```
渲染层：内容变化 → 实测内容高 → nc-resize(h)
主进程：show 之前 → 发 nc-measure 强制要一次真实高度 → 收到后立即 show
```

- 主进程**不再用 520 / 上次高度做占位**，只做 200ms 极端兜底。
- 窗口锚定屏幕右下角（`getNcRect` 底边固定），所以高度增长时**底边不动、向上生长**。

### 2.4 为什么 SYNC 也要保留一条「兜底开窗」的能力（D13）

原始设计里 I1 是绝对的：`SYNC_UNREAD` 无权开窗，只有网页端的 `SHOW_MESSAGE_NOTIFICATION` 能开。
这条不变量成功地根治了抖动，但把**全部提醒**押在网页端一段逻辑上。

实测日志证明这个单点会断：v6 SDK 下 `layout.vue` 用 `watch(..., { deep: true })` 的
`oldValue` 做「未读是否增长」的判断，而深层响应式数组的 oldValue 与 newValue **指向同一引用**，
`newConv.unreadCount > oldConv.unreadCount` 恒为 `false`。
结果：`SYNC_UNREAD` 一直在发，`SHOW_MESSAGE_NOTIFICATION` **一次都没发过** → 桌面端完全静音。

因此保留一条条件极窄的兜底：

```
syncUnread 检测到 cid 的 count 比上次同步大  →  视为真实新消息  →  入栈 + 响铃 + 展示
前提：非首次同步（基线已建立）、非免打扰、非正在查看该会话
```

为什么这样不会重新引入抖动：

- 双通道都正常时，`SHOW` 先到已经把会话入栈并响铃，兜底再遇到同一会话时
  `addToStack` 返回 `false` 且 `ringed` 已含该会话 → 直接跳过（`Sync-fallback skip`）。
- 兜底只「加」不「减」，不会清空栈，因此不会出现「弹出→被清→再弹」。
- 首次同步（含空列表）只建立基线，历史未读依旧不弹（S5.5）。

代价：网页端若出现未读数「抖动上涨」（如多端各报一次），可能多弹一次提醒。
多客户端歧义已由 I5（`isMirrorClient`）在入口处消除，实际风险很低；
相比之下「一条都不弹」的代价显然更高。

## 4. 状态机

```
                 pushMessage(允许展示)
     ┌────────┐ ───────────────────────▶ ┌─────────┐
     │  idle  │                          │ arming  │  (150ms 首屏合并)
     └────────┘ ◀─────────────────────── └─────────┘
        ▲   ▲      arm 期间全部已读            │
        │   │                                  │ 到点 + nc-measure 回传
        │   │                                  ▼
        │   │                            ┌─────────┐
        │   └──── 超时 / ✕ / 点完 ─────── │  shown  │ ── pushMessage(新增/更新) ──┐
        │        （进入 1.2s 冷却）       └─────────┘ ◀────── 重置计时 ───────────┘
        │                                     │
        └──── SYNC 判定栈空（已读）────────────┘
```

**不变量（Invariant）**

1. `idle → shown` 只有两条路径：`pushMessage`（网页端真实新消息）、`syncUnread` 检测到**未读增长**（兜底，见 §2.4）。
2. `shown` 期间**绝不** `hide()`，只 `setBounds()`。
3. `nc-measure` 返回的高度是唯一可信高度。
4. 关栈后 1.2s 内，`SYNC_UNREAD` 不得开栈。

## 6. 人工验收清单（打包前必过）

1. 找一个人连续发 2 条 → 1 行，计数 2，只响 1 次铃。
2. 找两个人各发 1 条（间隔 1 秒）→ 2 行堆叠，第 1 行不消失。
3. 两个人连发（间隔 5 秒以上）→ 每次都是完整 2 行，不交替闪现。
4. 点第 1 行 → 跳会话，该行消失，第 2 行仍在。
5. 点 ✕ → 立刻消失，1 秒内不自己冒出来。
6. 打开一个会话来消息 → 不弹窗。
7. 把窗口用其他窗口盖住 → 新消息到达时仍在最上层。

## 7. 产品决策记录（2026-10-22 定稿）

> **决策原则：以用户体验为重。** 冲突时的优先级：
> **不漏 > 不闪 > 能分辨（是谁、几条） > 少打扰**。
> 「少打扰」排最后不是不重视，而是用户的核心抱怨是「漏」和「闪」——
> 提醒窗多响一次是可忍的，错过一条消息是不可忍的。

### D-1 首屏合并 150ms —— 接受这点延迟

两个会话在 150ms 内先后到达时，窗口**延后 150ms** 才出现，换取「两行一次成型」。

- 人的感知阈值约 200ms，150ms 无感；而「先出 1 行、再长高」是**明确可见**的跳变。
- 成本极低、收益明确。不合并的代价是视觉抖动，合并的代价是不可感知的延迟。

### D-2 响铃以「栈」为单位，不以「固定时间」为单位

- 窗口开着（用户眼前就有提示）→ **同一会话不再响**
- 栈关闭后再来（用户可能已经走开）→ **重新响**
- 不设「30 秒内不再响」这类固定窗口

理由：铃声的语义是「把你叫过来」。人已经在看，不必再叫；窗口关了说明可能离开了，必须再叫。
按时间算会出现两种都错的情况：人走了 40 秒才来消息却不响（漏），人还盯着屏幕 20 秒内又响（吵）。

### D-3 超过 6 个会话 → 滚动，不折叠

窗口高度封顶 520px（约 6 行），第 7 个会话起列表内滚动；新会话插到顶部并**自动滚回顶部**。

不采用「还有 N 个会话」折叠——折叠隐藏了「是谁」，而提醒窗的核心价值就是「谁找我」。
滚动保留全部信息，且新消息始终可见。

### D-4 点开某个会话 → 其余行保留并续期

不采用系统通知常见的「点一条清全部」。

这是「多人同时找我」的场景，点开一个不代表其他人不重要。剩余行保留并重置为完整时长；
只有**最后一行**被点掉时才收起窗口。

### D-5 免打扰会话 → 只更新托盘，不弹不响

「不打扰」不等于「不统计」。托盘上的数字是被动信息，不构成打扰；
把它一起隐藏，会让人误以为「没人找我」，这属于信息错误而不是减少打扰。

### D-6 展示时长随行数递增

设定值（3~10s）语义明确为**一行**的扫读时间。实际时长：

```
实际秒数 = min(12, max(3, 设定值) + (行数 - 1))
```

理由：6 个会话堆叠时按 5 秒消失，用户连「是谁」都读不完，等于白弹。
上限 12s 防止提醒窗长期占屏（用户在专心做别的事时会烦）。

### D-7 会话 id 缺失时禁止破坏性操作

点提醒但拿不到 `conversationId` 时，只做保守处理，绝不「全部已读」。

> 旧实现 `markRead(convId || 'all')` 在 id 为空字符串时会把**整个列表清空**，误伤其它会话。
> 宁可这一行不消失，也不能连带清掉别人的提醒。
