# 邮箱功能（e日志 桌面端）方案设计

> 状态：待评审  
> 范围：e日志 桌面端（desktop-notifier，Electron）本地集成 QQ邮箱 与 阿里云企业邮箱，并可被本机 WorkBuddy 读取。  
> 工期目标：核心收发最小闭环约 2–3 个工作日；MCP 读取另计约 1 天。  
> 资源决策（2026-10-12）：全部采用 **MIT / Electron 内置**免费库（imapflow + nodemailer + mailparser + 官方 MCP SDK 自写薄适配器）；**有意不引入**商业的 EmailEngine（需付费订阅 + Redis + 独立服务）与现成 MCP 邮件服务（底层同套库，MCP 自写更轻）。详见 4.1。

---

## 1. 背景与目标

- 在 e日志 桌面端集成邮箱，让用户方便地**查看 / 收发** QQ邮箱 与 阿里云企业邮箱。
- 长期目标（本期列为**核心需求**）：**让本机运行的 WorkBuddy（AI 助手）能按用户授权读取桌面端桥接的邮件数据**。
- 本期不新增后端服务：邮件桥运行在桌面端 Electron 主进程内，授权码留本机。

### 已确定的边界

- 接入对象：***QQ邮箱 + 阿里云企业邮箱（标准版及以上）****。*
- *接入方式：****IMAP / SMTP + 授权码****（非 OAuth、非阿里邮箱 API 开放平台）。*
- 部署位置：**桌面端本地桥接**（不另起独立后端服务）。

---

## 2. 为什么放在桌面端（核心判断）

| 能力          | 网页端             | 桌面端（Electron）                         |
| ----------- | --------------- | ------------------------------------- |
| 握 IMAP 长连接  | ❌ 浏览器无原生 socket | ✅ 主进程 Node 网络库                        |
| 安全保管授权码     | ❌ 无法安全存敏感凭证     | ✅ `safeStorage`（DPAPI/Keychain）+ 本机文件 |
| 后台同步 / 实时收信 | ❌ 无常驻进程         | ✅ 主进程可做 IDLE / 轮询                     |
| 系统通知        | ⚠️ 受限           | ✅ 原生通知（复用现有机制）                        |

结论：桌面端天然具备"邮箱客户端"所需的全部能力；把桥做进桌面端**不另起后端、不用部署**，是成本最低的正经做法。以后若网页端也要看，把 `mailBridge` 抽成独立 Node 服务即可。

## 3. 总体架构

```
┌─────────────────────────────────────────────────────────────┐
│  e日志 桌面端 (Electron)                                      │
│                                                               │
│  ┌──────────────┐         IPC         ┌────────────────────┐  │
│  │ mail-window  │  ─────────────────▶ │  主进程 (Node)      │  │
│  │ (渲染进程)   │ ◀─────────────────  │                    │  │
│  │  Vue/HTML UI │  账号/文件夹/信/发   │  mailBridge        │  │
│  └──────────────┘                    │  (imapflow+nodemailer│
│                                       │   + 密钥管理)        │  │
│  ┌──────────────┐  本地 MCP(HTTP)     │                    │  │
│  │ WorkBuddy    │ ─────────────────▶ │  startMcpServer()   │  │
│  │ (本机 AI)    │ ◀─────────────────  │  (只读工具)         │  │
│  └──────────────┘                    └─────────┬──────────┘  │
└──────────────────────────────────────────────────┼──────────┘
                                                    │ IMAP/SMTP (SSL)
                              ┌─────────────────────┼─────────────────────┐
                              ▼                     ▼                     │
                       imap.qq.com:993      imap.qiye.aliyun.com:993       │
                       smtp.qq.com:465      smtp.qiye.aliyun.com:465       │
                       (QQ邮箱)             (阿里云企业邮箱)                │
```

- **mail-window**：沿用现有窗口模式（独立 HTML + `window.electronAPI` IPC），负责账号管理与邮件三栏 UI。
- **mailBridge（主进程）**：封装 IMAP/SMTP 连接、MIME 解析、凭证加密存储；同时是 UI 与 WorkBuddy 的唯一数据出口。
- **MCP server（主进程内 HTTP，绑定 127.0.0.1）**：把邮件能力以标准协议暴露给本机 WorkBuddy，UI 与 AI 共用同一套桥。

## 4. 技术选型与版本

| 用途      | 库                           | 版本（约） | 说明                                      |
| ------- | --------------------------- | ----- | --------------------------------------- |
| 收信      | `imapflow`                  | ^2.x  | 现代 IMAP 客户端，TLS 友好，支持 XOAUTH2 备用        |
| 发信      | `nodemailer`                | ^6.x  | SMTP 发送，支持 OAuth2 备用                    |
| MIME 解析 | `mailparser`                | ^3.x  | 解析正文 / 附件                               |
| 实时收信    | `mail-listener-flow`        | ^1.x  | 基于 IMAP IDLE（阶段 2 可选）                   |
| 凭证加密    | Electron `safeStorage`      | 内置    | Windows DPAPI / macOS Keychain 后端，免自管密钥 |
| MCP 服务  | `@modelcontextprotocol/sdk` | 最新    | 实现本地 HTTP/SSE MCP server                |

> 注意：桌面端 `package.json` 当前依赖极少（仅 pinyin-pro / solarlunar / ws），新增包需加入 `dependencies` 并 `npm install`；注意 Electron 32 的 ABI 兼容性（纯 JS 库无障碍）。
>
> **许可证与安全（已核实，2026-10-12）**：本方案全部选用 **MIT / Electron 内置** 资源，可闭源商用、无授权费。核心三件套 `imapflow` / `nodemailer` / `mailparser` 均出自同一可信作者（Andris Reinman，Nodemailer 作者），npm 官方标注 MIT、依赖 0 已知漏洞，且正是商业产品 EmailEngine 的底层引擎。MCP 层用官方 `@modelcontextprotocol/sdk`（MIT）自写薄适配器。详见 **4.1**。我们**有意不选**商业的 EmailEngine（需付费订阅 + Redis + 独立服务）与现成 MCP 邮件服务（底层同套库，MCP 自写更轻）。

## 4.1 免费 & 安全资源清单（已核实）

| 资源 | 类型 | 许可证 | 安全性 / 可信度依据 | 本方案角色 |
| --- | --- | --- | --- | --- |
| `imapflow` | npm 库 | **MIT** | 作者 Andris Reinman（Nodemailer 作者）；npm 官方 MIT；依赖 0 已知漏洞；是 EmailEngine 的 IMAP 引擎 | 收信（IMAP，含 IDLE） |
| `nodemailer` | npm 库 | **MIT** | 同上作者；周下载 ~1600 万；SMTP 发送事实标准 | 发信（SMTP） |
| `mailparser` | npm 库 | **MIT** | 同上作者；MIME 解析事实标准 | 解析正文 / 附件 |
| `@modelcontextprotocol/sdk` | npm 库 | **MIT** | 官方 MCP TypeScript SDK；用于写薄 MCP 适配器 | WorkBuddy 读取层 |
| Electron `safeStorage` | 内置 API | —（Electron 自带） | 系统级 DPAPI / Keychain 后端，密钥不由我们管 | 授权码加密落盘 |
| Node 内置 `http` / `express`(MIT) | 运行时 / 库 | MIT（express） | 仅本机 `127.0.0.1` 监听 | 主进程薄 REST API |

**决策要点**
- 上述全部 **MIT / 内置**，可闭源商用、无授权费。
- **刻意不采用 EmailEngine（Postalsys）**：它是**商业 source-available**，商用需付费订阅，且要 Redis 主库 + 独立服务，对桌面端嵌入偏重；而它底层用的正是 `imapflow` / `nodemailer` / `mailparser`。直接采用这套免费库，能力等价、零成本、更轻。
- **刻意不引入现成 MCP 邮件服务**（如 `yunfeizhu/mcp-mail-server`、`ai-zerolab/mcp-email-server`）：它们底层也是 `imapflow` / `nodemailer`，MCP 层按用户意图由我们自写薄适配器（~50 行）更轻、依赖更少；现成服务不会多出"基本功能"，反而多一个外部进程依赖。
- **供应链安全**：固定版本 + `package-lock.json`；只从这些成熟包取依赖，不引不明来源库；安装后跑 `npm audit`。

| QQ邮箱    | `imap.qq.com:993` (SSL)          | `smtp.qq.com:465` (SSL)          | 邮箱设置→账户→开启 IMAP/SMTP 后生成；**不能用登录密码**        |

## 6. 数据模型

```ts
interface MailAccount {
  id: string                 // uuid
  provider: 'qq' | 'aliyun'
  email: string
  imapHost: string
  imapPort: number           // 993
  smtpHost: string
  smtpPort: number           // 465
  encPassword: string        // 授权码密文（AES-256-GCM，由 safeStorage 加密）
  createdAt: number
}
```

- **明文授权码只在主进程内存中存在**；落盘为密文。
- 渲染进程 / MCP 返回的账号对象**均不含 `encPassword`**，也不含可解密的任何字段。

## 7. IPC 契约（渲染进程 ↔ 主进程）

所有邮箱操作经 `window.electronAPI` 调用主进程，主进程内解密授权码后连 IMAP/SMTP。

| 通道                    | 入参                                                                | 返回                                                 | 说明                        |
| --------------------- | ----------------------------------------------------------------- | -------------------------------------------------- | ------------------------- |
| `mail:addAccount`     | `{ provider, email, password(授权码明文,仅传一次), imapHost?, smtpHost? }` | `{ ok, id }`                                       | 先 `testConnection` 通过再存密文 |
| `mail:listAccounts`   | —                                                                 | `MailAccount[]`（无密文）                               | 设置页列表                     |
| `mail:removeAccount`  | `{ id }`                                                          | `{ ok }`                                           | 删除密文+内存                   |
| `mail:folders`        | `{ id }`                                                          | `Folder[]`                                         | 文件夹列表                     |
| `mail:messages`       | `{ id, folder, page, pageSize }`                                  | `{ items: MsgSummary[], total }`                   | 列表分页                      |
| `mail:message`        | `{ id, folder, uid }`                                             | `{ headers, text, html?, attachments: AttMeta[] }` | 单封完整内容                    |
| `mail:attachment`     | `{ id, folder, uid, partId }`                                     | `base64`                                           | 按需取，避免大附件全量               |
| `mail:send`           | `{ id, to, subject, text, html?, attachments? }`                  | `{ ok, messageId }`                                | 发送                        |
| `mail:testConnection` | `{ provider, email, password }`                                   | `{ ok, error? }`                                   | 添加前连通校验                   |

`MsgSummary = { uid, from, to, subject, date, seen, hasAttachment }`  
`AttMeta = { partId, filename, size, mime }`

## 8. UI 设计（mail-window.html + mail-window.js）

沿用现有"独立 HTML 窗口 + IPC"模式（参考 `workbench-window` / `settings-window`）。

- **账号管理页**：账号列表 + 新增（选 QQ / 阿里预设，填邮箱 + 授权码，点"测试连接"后保存）。
- **三栏布局**：左=文件夹，中=邮件列表（发件人 / 主题 / 时间 / 未读 / 附件标记），右=邮件详情。
- **阅读**：正文以**沙箱**渲染（禁用脚本、外链追踪像素用 `referrerpolicy=no-referrer` 或不加载远程图），附件列表可下载。
- **撰写**：弹层/页内撰写（收件人、主题、正文、附件）→ `mail:send`。
- **状态**：连接中 / 空态 / 错误态齐全。
- **安全**：授权码输入框为 `password` 类型，不回显、不写日志。

---

## 9. 安全设计（重点）

1. **授权码 = 高敏凭证**：仅主进程持有明文；落盘 `AES-256-GCM` 密文（经 `safeStorage` 管理密钥）；渲染进程/MCP 永不直接接触明文。
2. **传输**：IMAP/SMTP 强制 SSL/TLS（993/465），禁用明文端口。
3. **日志**：禁止打印授权码 / token；出错只记录错误类型，不记录敏感值。
4. **账号删除**：UI 删除 → 主进程删除密文与内存会话。
5. **多账号隔离**：每账号独立连接与会话，互不影响。
6. **MCP 边界（见第 11 节）**：仅绑定 `127.0.0.1`，可选 bearer token；只暴露当前用户配置的账号；返回数据不含任何凭证。

## 11. 供本地 WorkBuddy 读取邮件数据（核心需求）

### 11.1 目标与机制

让**本机运行的 WorkBuddy** 能按用户授权读取桌面端桥接的邮件数据。

做法：在桌面端主进程内启动一个**本地 MCP 服务器（HTTP/SSE，绑定 `127.0.0.1`）**，复用 `mailBridge` 的账号与连接能力，向 WorkBuddy 暴露**只读（及可选发送）工具**。WorkBuddy 通过标准 MCP 协议调用，无需直接碰授权码或 IMAP。

### 11.2 为什么用 MCP

MCP 是 AI 代理访问本地工具/数据的标准协议；WorkBuddy 已支持配置 MCP server（见 `~/.workbuddy/mcp.json`）。相比"写文件让助手读"，MCP 更结构化、可受控、可审计、可限域。

### 11.3 MCP 工具清单（建议）

| 工具                      | 入参                                                      | 返回                       |
| ----------------------- | ------------------------------------------------------- | ------------------------ |
| `mail_list_accounts`    | —                                                       | 已配置账号列表（**无凭证**）         |
| `mail_list_folders`     | `{ accountId }`                                         | 文件夹列表                    |
| `mail_list_messages`    | `{ accountId, folder?, page, pageSize, unreadOnly? }`   | 邮件摘要列表                   |
| `mail_get_message`      | `{ accountId, folder, uid }`                            | 完整邮件（正文 text/html、附件元信息） |
| `mail_search_messages`  | `{ accountId, query, folder? }`                         | 关键词搜索结果                  |
| `mail_send_message`（可选） | `{ accountId, to, subject, text, html?, attachments? }` | 发送结果                     |

### 11.4 安全与授权边界

- 仅绑定 `127.0.0.1`（本机），不对外暴露。
- 可选 bearer token（桌面端生成并写入 WorkBuddy `mcp.json`），防止本机其他进程随意调用。
- 授权码永远只在主进程内解密使用；MCP 返回数据不含凭证。
- 作用域：只暴露当前桌面端已登录用户配置的账号；不跨用户。
- 审计：MCP 调用可记录（账号级 / 工具级），便于追溯助手读了什么。

### 11.5 WorkBuddy 接入（示意，写入 `~/.workbuddy/mcp.json`）

```json
{
  "mcpServers": {
    "e日志邮箱": {
      "url": "http://127.0.0.1:18765/mcp",
      "headers": { "Authorization": "Bearer <token>" }
    }
  }
}
```

> 具体字段以 WorkBuddy 当前 MCP 配置格式为准，动手前核对（stdio 型则为 `command`/`args`）。

### 11.6 实现位置

- 在 `mailBridge` 内增加 `startMcpServer()`，复用同一套 IMAP/nodemailer 连接与账号 store。
- 使用 `@modelcontextprotocol/sdk` 实现 HTTP/SSE server。
- 仅当桌面端运行且用户已配置邮箱时可用；端口占用时向后探测可用端口。

## 13. 风险与注意

- **阿里云企业邮箱**：免费版不支持 API 开放平台，但 IMAP 授权码可用（需管理员开启 IMAP 权限，且账号未被限制三方登录）。
- **QQ**：必须开启 IMAP/SMTP 服务并生成授权码，登录密码不可用。
- **大附件 / 大量邮件**：列表分页、附件按需拉取、HTML 正文沙箱（禁用脚本、谨慎加载远程图）。
- **网络**：993/465 出网策略；桌面端内网 / 代理环境需实机测试。
- **并发连接**：多账号连接池 / 超时管理，避免资源占用过高。
- **MCP 端口冲突**：固定端口 + 占用时向后探测。

## 15. 方案权衡（为什么不是别的）

- **不在网页端做**：握不住 IMAP 连接、授权码无法安全存、无后台进程 —— 见第 2 节。
- **不另起独立后端桥接服务**：本期目标是"桌面端看到"，把桥做进 Electron 主进程即可，**零部署**；以后要 web 再看，再把 `mailBridge` 抽成服务。
- **不用阿里邮箱 API 开放平台**：其为 `client_credentials` **组织级**凭据（一个 secret 开全公司邮件），安全模型更重；本期用按用户**授权码**更贴合"个人邮箱"场景，且任意版本可用。
- **不用 Gmail/Outlook OAuth**：本期优先级不含这两家；imapflow/nodemailer 已预留 XOAUTH2，后续可加。
- **不用 EmailEngine（Postalsys）**：虽是功能最完整的 headless 邮件服务，但为**商业 source-available**，商用需付费订阅，且要 Redis 主库 + 独立服务，桌面端嵌入偏重；其底层正是本方案采用的 imapflow/nodemailer/mailparser，直接取免费库能力等价、零成本、更轻。
- **不引入现成 MCP 邮件服务**（如 yunfeizhu / ai-zerolab 等）：它们底层也是 imapflow/nodemailer，MCP 层按用户意图由我们自写薄适配器（~50 行）更轻、依赖更少；现成服务不会多出"基本功能"，反而多一个外部进程依赖。
