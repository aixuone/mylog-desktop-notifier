会议互动画板 · 技术方案汇报

适用范围 e日志 视频会议（Web + Electron 桌面端） 日期 2026-09-30 状态 已联调可用 / 待办 1 项

结论速览

  • 技术路线：完全自研，零新增依赖。渲染用原生 Canvas 2D，同步复用会议已有的房间信令通道（TUIRoomKit 自定义消息），不引入任何新 SDK、新服务。
  • 是否收费：画板功能本身不产生任何费用，无新增许可与计费项。相关成本只有会议既有的音视频时长费，其中屏幕共享本身按视频时长计费（TRTC 既有规则，与画板无关）。
  • 两个显示面互斥：网页内画板（贴合会议画面）与 OS 级屏幕画板（Electron 透明覆盖窗，可覆盖整个桌面）二选一，由「本机是否正在共享屏幕」自动分流。
  • 同步策略：发「笔迹段」而非逐点，一次落笔一条消息，天然规避频控；坐标 0–1 归一化，跨分辨率对齐。

一技术路线与计费

1.1 技术路线

画板是挂在会议之上的一层轻量批注层，整条链路只用了会议既有的能力，没有引入新服务：

层次选型说明
绘制 / 渲染 原生 Canvas 2D 网页画板双层 canvas：底层画底图（截图/上传），上层画笔迹；橡皮擦用 destination-out 只擦笔迹、不伤底图
多人同步 会议房间自定义消息 TUIRoomEngine.sendCustomMessage() / on('onReceiveCustomMessage')，businessId = interactive_board。复用会议室已有的长连接，无需自建信令
显示面 A（网页） Vue3 浮层 + 双层 canvas InteractiveBoardPanel.vue，Teleport 到 body，动态贴合「会议画面内容区」
显示面 B（系统级） Electron 透明覆盖窗 board-overlay.html 跑在独立 BrowserWindow（transparent + alwaysOnTop:'screen-saver' + skipTaskbar），可覆盖整个桌面与其它应用
桌面桥接 IPC（preload 白名单） 网页 ↔ 主进程 ↔ 覆盖窗 三方的状态下发与笔迹回传

为什么不用现成的「互动白板」产品

  • 腾讯云互动白板 TIW 是独立计费的单独产品，功能重（多页、文档转码、实时音视频同步白板），与本需求不匹配。
  • 项目里确实存在一个 whiteboard.vue（引用官方 WhiteboardView 组件），但本互动画板与它无关，没有走那条路径。
  • 本需求本质是「在会议画面上圈画批注」，复用既有信令即可闭环，引入新 SDK 只会增加成本与风险。

1.2 是否收费

分两层看，结论是画板不新增任何计费项：

（1）画板功能本身：不额外收费

  • 不引入新 SDK、新云服务、新计费项；
  • 同步走的是会议房间的自定义消息通道，自定义消息不单独计费；
  • 不涉及云端录制、混流转码、AI 字幕等增值服务，因此也不触发这些额外账单。

（2）承载它的底层能力：沿用 TRTC / TUIRoomKit 既有计费

画板依附于视频会议，会议本身的计费口径不变。当前腾讯云官方价格如下（2026-09 官网口径，实际以合同与官网为准）：

三个必须知道的计费事实：
  • 屏幕共享是单独一路视频流，按视频时长计费。用户订阅到共享画面时即按视频档位（标清/高清/全高清）计价。这是 TRTC 既有规则，「屏幕画板」场景下共享行为本身的成本与画板无关。
  • TUIRoomKit 正式版需 IM 专业版/旗舰版 + TRTC 包月套餐同时生效（含 UI 低代码方案的开通条件）。
  • 免费额度：新账号可领 10,000 分钟音视频时长试用；TUIRoomKit 另有 7 天体验版（每个 SDKAppID 可领 2 次），适合评审/演示阶段零成本验证。
一句话给负责人：画板是「复用既有会议信道的自研批注层」，0 新增许可、0 新增计费项；唯一相关的成本是屏幕共享视频流的时长费，而那是会议本来就有的支出，不因画板而增加。

2.3 关键设计决策

设计点做法解决的问题
同步单位 发「笔迹段」而非逐点 消息量小、无节流抖动、重放简单；天然远低于频控上限
发送时机 仅 pointerup 广播 一次交互 = 一条消息，避免 move 事件刷屏
坐标系 0–1 归一化（相对画面内容区） 跨分辨率、跨窗口尺寸对齐；解决 letterbox 下多人笔迹错位
笔迹错位根因处理 反推 object-fit: contain 后的真实画面矩形 贴合「画面内容区」而非「视频容器」，避免黑边导致偏移
后进会者 snapshot-request / snapshot 全量补发 解决「后进来的人看不到已有笔迹」
会议级画板开关 board-open（附现状全量）/ board-close 一人开画板，全员自动进入并看到现状；共享结束自动收口
橡皮擦不伤底图 双层 canvas + destination-out 擦除只作用于笔迹层，截图/上传的底图不被破坏
本端即时反馈 先本地 push 重绘，再发消息 绘制「零延迟」，网络只影响他人看到的时机

2.4 两个显示面如何互斥与切换

同一用户同一时刻只会有一种画板表面，由「本机是否正在共享屏幕」分流。状态真源是 TUIRoomKit 自带的 useDeviceState().screenStatus（该状态仅在事件属于本地登录用户且为屏幕流时才置 On）——而不是参会人条目上的 hasScreenStream（屏幕共享在引擎里是「独立参会人」，本人的该字段并不可靠）。

三数据定义

3.1 核心数据结构

// ── 工具类型 ──────────────────────────────
type BoardTool = 'pointer' | 'pen' | 'eraser' | 'line' | 'rect' | 'circle' | 'image'

// ── 坐标：归一化 0-1，相对「画面内容区」，保证跨端对齐 ──
interface Point { x: number; y: number }

// ── 笔迹 ──────────────────────────────────
interface Stroke {
  id: string          // `${selfId}_${Date.now()}_${rand}`，全局唯一，用于去重与撤销
  userId: string        // 绘制者，用于「撤销只撤自己那笔」
  userName: string      // 展示用
  tool: BoardTool
  color: string        // #rrggbb（8 色调色板）
  size: number         // 1–20，默认 4
  points: Point[]      // pen/eraser＝完整路径点；line/rect/circle＝[起点, 终点]
}

// ── 图片笔迹（截图底图 / 上传图片）────────────
interface ImageStroke {
  id: string
  userId: string
  userName: string
  tool: 'image'
  src: string          // 预研：base64 dataURL；正式版：COS URL
  ratio: number        // 原始宽高比 w/h，用于 contain 适配
  cx: number         // 归一化中心 x（0-1）
  cy: number         // 归一化中心 y（0-1）
  w: number          // 归一化宽度（高度由 ratio 推导）
}

3.2 同步消息协议

通道：TUIRoomEngine.sendCustomMessage({ businessId: 'interactive_board', data })，data 为 BoardMsg 的 JSON 串。接收端统一走 onReceiveCustomMessage 并按 type 分发。

type BoardMsg =
  | { type: 'stroke';           stroke: Stroke }                        // 新增一笔
  | { type: 'image';            image: ImageStroke }                   // 新增图片笔迹
  | { type: 'undo';             strokeId: string }                   // 按 id 精确删除一笔
  | { type: 'clear' }                                                    // 清空全员笔迹
  | { type: 'board-open';       strokes: Stroke[]; images: ImageStroke[] } // 开画板 + 现状全量
  | { type: 'board-close' }                                              // 结束会议画板
  | { type: 'snapshot-request' }                                         // 后进会者拉历史
  | { type: 'snapshot';         strokes: Stroke[]; images: ImageStroke[] } // 历史全量回包
消息方向载荷语义
stroke广播Stroke一笔落下（pointerup 时发）
image广播ImageStroke截图底图或上传图片
undo广播strokeId按 id 精确删除，不靠「最后一笔」推断
clear广播—清空所有人笔迹与图片
board-open广播strokes + images会议级画板开启，附带现状全量，他人即时进入
board-close广播—画板结束，全员清空关闭
snapshot-request点发—进会后 1.5s 发出，向已有内容的端要历史
snapshot点发strokes + images有内容的端回全量

3.3 容量与频控约束

约束项限制值本方案的应对
单条消息大小 12 KB（腾讯 IM / 房间信令消息上限，超限错误码 100603） 笔迹消息体极小（数 KB 以内）；图片因 base64 膨胀约 33%，需压缩：截图 640px / quality 0.5、上传图 1280px / quality 0.6
消息频率 群消息 40 条/秒（每房间独立限频） 仅 pointerup 发一条，单人手速远低于上限；多人同时绘制的叠加量也在安全区
图片高清底图 受 12 KB 上限约束，base64 只能传缩略图 正式版改走 COS URL：消息体只传 URL，底图保留原始分辨率
消息丢弃 超频时服务端返回 MsgDropReason（频控丢弃） 发送失败静默忽略，不影响本地绘制；配合 snapshot 机制具备自愈能力
已知待收敛项：图片底图目前以 base64 走消息通道（预研形态），受 12 KB 限制只能传缩略图。设计上已预留切换点——ImageStroke.src 字段本就同时支持 base64 与 COS URL，正式版只需把 captureVideoFrame/compressImage 的产物换成上传后的 URL，协议与渲染层无需改动。
